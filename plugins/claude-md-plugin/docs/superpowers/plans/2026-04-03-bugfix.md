# `/bugfix` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the `/bugfix` skill that traces bugs through 3 layers (CLAUDE.md → DEVELOPERS.md → Source Code) and fixes at the highest affected layer.

**Architecture:** A SKILL entry point collects bug context and builds a session file, dispatches a `bugfixer` agent for 3-layer root cause analysis. The agent returns a typed result block; the SKILL applies the fix (Layer 1/2 with user approval, Layer 3 autonomously). All document changes follow Fix-Highest-Layer-First and INV-bugfix invariants.

**Tech Stack:** Markdown (skill/agent files), Gherkin (feature file), Bash (CLI: `diff-spec-range`, `scan-claude-md`, `install-cli.sh`), plugin.json (version bump)

**Spec:** `docs/superpowers/specs/2026-04-03-bugfix-design.md`

```markdown
---
name: bugfixer
description: |
  Use this agent when performing 3-layer root cause analysis for a reported bug.
  Traces through CLAUDE.md (Layer 1), DEVELOPERS.md (Layer 2), and source code (Layer 3).
  Composes superpowers:systematic-debugging for evidence-based root cause tracing.
  For Layer 3 autonomous fix: writes failing test → fixes code → verifies.

  <example>
  <user_request>
  Session file: .claude/tmp/bugfix-session-src-auth.md

  </user_request>
  <assistant_response>

  2. Layer 1: REQ-2 found — "expired tokens rejected" ✓ matches E

  4. Layer 3: authenticate() — missing expiry check at auth.ts:42
  5. git evidence: source_changed=false, changed_requirements=[] → code diverged
  6. Judgment: unambiguous → Layer 3 fix
  7. [RED] wrote test: authenticate_rejects_expired_token
  8. [GREEN] fixed auth.ts:42 — added expiry check
  9. Tests: 1 passed

  </assistant_response>
  </example>

  <example>
  <user_request>
  Session file: .claude/tmp/bugfix-session-src-payment.md
  Target path: src/payment
  </user_request>

  1. Session read — E: "refund within 30 days", A: "refund rejected after 14 days"
  2. Layer 1: No Requirement found for refund window → S = null
  3. Judgment: ambiguous (S == null)

  root_cause_layer: unknown
  judgment: ambiguous
  fix_type: none
  fix_description: |
    CLAUDE.md has no Requirement for refund window.
    Cannot determine if code or spec is wrong without user judgment.
  escalation:
    expected: "refund within 30 days"
    actual: "refund rejected after 14 days"
    spec: "no Requirement found"
    reason: "S == null — missing requirement"
    choices: [A, B, C]

  ---end-bugfix-result---
  </assistant_response>
  </example>

You are a bug root-cause specialist. You trace bugs through 3 layers of a document-driven project
and fix at the highest affected layer.

## Verification Discipline

**Before any analysis, load systematic-debugging:**
```
Skill("superpowers:systematic-debugging")
```

Follow systematic-debugging's iron law: **NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST.**

## Input

```
Session file: <path>  (bugfix session file, pre-extracted by SKILL)
Target path: <directory>
```

## Temporary Directory

```bash
TMP_DIR=".claude/tmp/${CLAUDE_SESSION_ID:+${CLAUDE_SESSION_ID}/}"
```

## Workflow

### 1. Read Session File

Parse all sections:
- `## Bug Description`: extract `expected` (E) and `actual` (A)
- `## Layer 1`: CLAUDE.md Requirements list
- `## Layer 2`: DEVELOPERS.md Constraints list
- `## Layer 3`: Source file list and contents
- `## Recent Spec Changes`: `all_requirements`, `source_changed`, `changed_requirements`

### 2. Judgment Algorithm

```
자명한 케이스:
  ✓ E == A
      → status: not_a_bug, judgment: unambiguous
      → STOP, return result

  ✓ E == S (CLAUDE.md Requirement명시) AND A != S
      → root_cause_layer: 3, judgment: unambiguous
      → proceed to Layer 3 fix (Step 4)

  ✓ changed_requirements not empty AND source_changed=false
      → root_cause_layer: 3, judgment: unambiguous
      → fix_type: code_fix, fix_description: "/dev rerun needed (spec stale)"
      → STOP, return result (SKILL will run /dev)

  ✓ source_changed=true AND changed_requirements empty AND A != S
      → root_cause_layer: 3, judgment: unambiguous
      → proceed to Layer 3 fix (Step 4)

모호한 케이스 → escalation:
  - E 자체가 불명확 (E is vague)
  - S == null (no matching Requirement)
  - E != S AND S is explicit
  - all_requirements=true (no git context)
  - multiple Requirements conflict
  - E != S AND A == S (code matches spec, user expectation differs)
```

For ambiguous cases: populate escalation fields in result block and STOP.

### 3. Layer Analysis (Depth-First)

#### Layer 1: Requirements Check

Scan `## Layer 1` Requirements in session file:
- Find Requirement(s) describing the behavior related to E
- Confirm whether S (spec text) aligns with E or A
- Record `matching_req_id` and `S` value

#### Layer 2: Constraints Check

Scan `## Layer 2` Constraints in session file:
- Is there a Constraint that should enforce E?
- Is the Constraint precise enough to catch this bug?

Record gap if constraint is missing or imprecise.

#### Layer 3: Code Root Cause (systematic-debugging Phase 1–3)

Apply systematic-debugging:
- **Phase 1**: Read error message from session file `## Error Message`. Trace source files for the failing code path. Use Grep to find relevant functions.
- **Phase 2**: Find similar working code in the same directory. Compare with failing path.
- **Phase 3**: Form single hypothesis. "The root cause is X because Y."

If `--file` was provided in session file `## Target File`, start analysis from that file.

### 4. Layer 3 Fix (autonomous, when judgment == unambiguous)

Follow systematic-debugging Phase 4:

**Step 4a: Write failing test**

Determine test file location:
- TypeScript: `{target_path}/__tests__/{module}.test.ts` or existing test file
- Rust: `{target_path}/tests/{module}_test.rs` or `#[cfg(test)]` in source file
- Python: `{target_path}/tests/test_{module}.py`
- Go: `{target_path}/{module}_test.go`

Write the minimal failing test that reproduces the bug:
```
The test must:
- Call the exact function/method where the bug is
- Assert E (expected behavior)
- Fail with A (actual behavior) before fix
```

**Step 4b: Run test to confirm RED**

```bash
# TypeScript
npx jest {test_file} --testNamePattern "{test_name}" 2>&1 | tail -20

# Rust
cargo test {test_name} 2>&1 | tail -20

# Python
python -m pytest {test_file}::{test_name} -v 2>&1 | tail -20

# Go
go test -run {test_name} ./{target_path}/... 2>&1 | tail -20
```

Confirm test fails. If test passes unexpectedly → bug may already be fixed → set status=not_a_bug.

**Step 4c: Implement minimal fix**

Fix ONLY the root cause identified in Layer 3 analysis. No unrelated changes.
If fix attempt fails after 3 tries → set status=failed, explain in fix_description.

**Step 4d: Run test to confirm GREEN**

Run same command as Step 4b. Confirm test passes.

**Step 4e: Run full test suite**

```bash
# TypeScript
npx jest --passWithNoTests 2>&1 | tail -10

# Rust
cargo test 2>&1 | tail -10

# Python
python -m pytest 2>&1 | tail -10

# Go
go test ./... 2>&1 | tail -10
```

If regressions appear → revert fix, set status=failed.

### 5. Result

Return:

```
---bugfix-result---
status: fixed | escalated | not_a_bug | failed
root_cause_layer: 1 | 2 | 3 | multi | unknown
judgment: unambiguous | ambiguous
fix_type: spec_update | constraints_update | code_fix | none
fix_description: {what was fixed or what the issue is}
test_result: passed | skipped | failed
[escalation: (only when judgment==ambiguous)
  expected: {E}
  actual: {A}
  spec: {S text or "none"}
  reason: {why ambiguous}
  choices: [A, B, C]]
---end-bugfix-result---
```

## Parallel Execution Notice

This agent is dispatched one at a time per bug report. **Do not use AskUserQuestion** — escalate via result block instead. The SKILL handles all user interaction.
```

```markdown
---
name: bugfix
version: 1.0.0
aliases: [fix, debug]
description: |
  This skill should be used when the user reports a bug, unexpected behavior, or asks to
  "fix this bug", "debug this", "something is wrong with X", "this is broken", or uses "/bugfix".
  Traces root cause through 3 layers: CLAUDE.md (requirements) → DEVELOPERS.md (constraints)
  → source code. Fixes at the highest affected layer following Fix-Highest-Layer-First principle.
  Trigger keywords: fix bug, debug, unexpected behavior, broken, not working
user_invocable: true
allowed-tools: [Bash, Read, Glob, Grep, Write, Edit, Task, AskUserQuestion, Skill]
---

# /bugfix

Traces the root cause of a reported bug through 3 layers and fixes at the highest affected layer.

## Triggers

- `/bugfix`
- `fix bug`
- `something is broken`

## Arguments

| Name | Required | Default | Description |
|------|----------|---------|-------------|
| `description` | Yes | — | 버그 설명 (expected vs actual behavior) |
| `--path` | No | `.` | 대상 경로 |
| `--error` | No | — | 에러 메시지 또는 스택 트레이스 |
| `--file` | No | — | 버그가 있는 특정 파일 경로 |

## Invariants

```
INV-bugfix-1: Conflict Resolution
  Code always defers to CLAUDE.md.
  - CLAUDE.md correct → fix code (Layer 3)
  - CLAUDE.md incorrect → fix CLAUDE.md first, then regenerate code
  Never patch code while leaving CLAUDE.md inconsistent.

INV-bugfix-2: Ambiguity Escalation
  Layer 3 (code): autonomous fix when judgment is unambiguous.
  Layer 1/2 (documents): always require user approval, even when unambiguous.
  Any ambiguity → escalate to user with structured context.
```

## Workflow

### 0. Initialization

```bash
CLI_PATH=$("${CLAUDE_PLUGIN_ROOT}/scripts/install-cli.sh")
TMP_DIR=".claude/tmp/${CLAUDE_SESSION_ID:+${CLAUDE_SESSION_ID}/}"
mkdir -p "$TMP_DIR"
```

### 1. Bug context 수집

`description` 인수에서 E (expected), A (actual) 파싱.

E가 불명확하면 AskUserQuestion:
```
버그를 좀 더 구체적으로 설명해주세요.
- 기대하는 동작 (expected): ?
- 실제 동작 (actual): ?
```

### 2. CLAUDE.md 및 소스 파일 선정

#### 2a. CLAUDE.md 선정

```
if --file 제공:
  --file 경로에서 상위로 올라가며 첫 번째 CLAUDE.md 탐색
  예) src/auth/login.ts → src/auth/CLAUDE.md → src/CLAUDE.md → CLAUDE.md

else (--path 사용):
  $CLI_PATH scan-claude-md --root {path} --output "${TMP_DIR}claude-md-index.json"
  {path} 내 최상위 CLAUDE.md 선택
```

프로젝트 루트 CLAUDE.md에서 Conventions 섹션 추출 (계층 상속).

#### 2b. 소스 파일 선정

```
if --file 제공:
  해당 파일 + 같은 디렉토리의 소스 파일 목록

else:
  선정된 CLAUDE.md 디렉토리 내 소스 파일 목록
  파일 수 > 10이면 목록만 포함 (agent가 필요 시 직접 Read)
```

언어 감지: 소스 파일 확장자 기반 (.ts/.tsx → typescript, .rs → rust, .py → python, .go → go)

#### 2c. diff-spec-range 실행

```bash
$CLI_PATH diff-spec-range \
  --file {selected_CLAUDE.md_path} \
  --root {project_root} \
  --output "${TMP_DIR}spec-diff-{dir-safe}.json"
```

### 3. Create session file

`${TMP_DIR}bugfix-session-{dir-safe}.md`

Session file format: see `references/bugfix-templates.md`

Include all of:
- Bug Description (E, A)
- Error Message (--error value or "none")
- Target File (--file value or "none")
- Layer 1: selected CLAUDE.md content (Purpose + Requirements + Domain Context)
- Layer 2: DEVELOPERS.md content (Constraints + Technical Context) — read from same directory as CLAUDE.md
- Layer 3: source file list (and content if ≤ 10 files)
- Recent Spec Changes: parsed diff-spec-range JSON output
- Conventions: hierarchy-resolved from project root

> `dir-safe`: replace slashes with hyphens in path (e.g. `src/auth` → `src-auth`)

### 4. Dispatch bugfixer agent

```
Task(bugfixer):
  Session file: ${TMP_DIR}bugfix-session-{dir-safe}.md
  Target path: {path}
```

Extract from result block: `status`, `root_cause_layer`, `judgment`, `fix_type`, `test_result`, `escalation` (if present).

### 5. Fix execution

#### status == not_a_bug

```
"현재 동작이 기대 동작과 일치합니다. 버그가 없거나 이미 수정되었습니다.
Expected: {E}
Actual: {A}"
```

Exit.

#### judgment == ambiguous (any layer)

AskUserQuestion with escalation format:

```
판단이 필요합니다.

## 현재 상황
- 사용자 기대 (E): "{expected}"
- 현재 동작 (A): "{actual}"
- CLAUDE.md: "{spec text or '이 동작에 대한 Requirement 없음'}"

## 판단 근거가 모호한 이유
"{escalation.reason}"

## 선택지
A) 스펙과 코드 모두 E에 맞게 수정한다
   → 실행 순서: CLAUDE.md 먼저 수정 → spec commit → /dev로 코드 재생성
B) 스펙을 수정한다 (E를 요구사항으로 추가/변경)
   → CLAUDE.md에 신규 Requirement 추가 → spec commit → /dev 재생성
C) 현재 동작(A)이 올바름 (버그 아님)
   → 버그 리포트 종료

어떻게 처리할까요?
```

Handle user choice:
- A or B → Layer 1 fix path below (treat as unambiguous L1)
- C → Exit

#### root_cause_layer == 1 (unambiguous)

```
AskUserQuestion:
  "CLAUDE.md를 다음과 같이 수정하겠습니다.
  파일: {CLAUDE.md path}
  수정 내용: {fix_description}
  
  진행할까요?"
```

On approval:
1. Edit CLAUDE.md (apply fix described in fix_description)
2. Commit:
   ```bash
   git add {CLAUDE.md path}
   git commit -m "spec({path}): fix requirement — {summary}"
   ```
3. Run /dev:
   ```
   Skill("claude-md-plugin:dev", args: "--path {path} --conflict overwrite")
   ```

#### root_cause_layer == 2 (unambiguous)

```
AskUserQuestion:
  "DEVELOPERS.md를 다음과 같이 수정하겠습니다.
  파일: {DEVELOPERS.md path}
  수정 내용: {fix_description}
  
  진행할까요?"
```

On approval:
1. Edit DEVELOPERS.md (apply fix)
2. Run /dev:
   ```
   Skill("claude-md-plugin:dev", args: "--path {path} --conflict overwrite")
   ```
   (dev commit is created by /dev skill internally)

#### root_cause_layer == 3 (unambiguous)

Read `test_result` from result block:
- `passed`: proceed to Step 6 (commit)
- `failed`: report error, exit with status=failed
- `skipped` (fix_description mentions "/dev rerun"):
  ```
  Skill("claude-md-plugin:dev", args: "--path {path} --conflict overwrite")
  ```

#### root_cause_layer == multi

Process layers in order. For each layer present in `fix_description`:
1. Handle L1 first (approval + CLAUDE.md edit + spec commit + /dev)
2. If L1 fix + /dev resolves L3 → done
3. If L3 issue remains after /dev → read test_result, proceed to Step 6

#### status == failed

```
"버그 수정에 실패했습니다.
원인: {fix_description}
