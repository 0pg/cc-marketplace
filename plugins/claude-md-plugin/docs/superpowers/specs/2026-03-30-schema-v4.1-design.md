# Schema v4.1 Design — 공개 API 계약 완전성 보장

**날짜**: 2026-03-30
**대상 버전**: DEVELOPERS.md Schema v4.1 (CLAUDE.md Schema 변경 없음)
**Breaking Change**: 없음 (모든 추가 섹션은 optional)

---

## 배경 및 목표

**목표**: CLAUDE.md + DEVELOPERS.md만으로 소스코드를 보지 않고 *공개 API 계약 수준에서* 시스템 전체 동작을 파악할 수 있어야 한다.

**현재 한계 (Socratic loop 도출)**:

| 영역 | 현재 상태 | 문제 |
|------|-----------|------|
| 공개 타입 정의 | Constraints 인라인 (`→ {userId, role}`) | 타입이 여러 곳에 흩어져 중복·불일치 발생 |
| 시스템 실행 흐름 | 없음 | 모듈 간 호출 순서를 알 수 없음 |
| 설정/환경변수 | Operations > 배포에 산재 | 타입·필수여부·기본값 파악 불가 |

---

## 설계 원칙 (Socratic 검증 완료)

1. **Optional 추가만** — 기존 DEVELOPERS.md는 schema-valid 유지 (breaking change 없음)
2. **기존 패턴 재사용** — `is_project_root` condition은 CLAUDE.md `## Instructions`와 동일한 메커니즘
3. **CLI 자동화 가능한 것은 자동화** — code_analyzer.rs에 이미 ExportedType, FunctionContract가 있음
4. **구현 세부사항 배제** — 언어, 예외처리 방식, 동기/비동기는 관심사 밖

## 변경 1: `## Data Schemas` (DEVELOPERS.md, 선택)

### 동기

Constraints 인라인 타입:
```markdown
- validateToken(token) → Claims{userId, exp, permissions}
- refreshToken(token) → TokenPair{accessToken, refreshToken}
- refreshToken(token) → AuthError{REFRESH_EXPIRED}
```

`Claims`, `TokenPair`, `AuthError`의 정확한 필드 구조를 이 세 줄만으로는 알 수 없다.
→ 타입 정의를 한 곳에 모으는 전용 섹션 필요.

### Socratic 검증

- **Q: 인라인으로도 충분하지 않나?** → A: validate-schema는 내용 엄격성을 강제 불가. 섹션 분리가 구조적 신호를 준다.
- **Q: code_analyzer가 타입을 추출하는가?** → A: `ExportedType` (interface/type/struct/enum) 이미 추출됨. `/decompile` 자동 생성 현실적.
- **Q: 별도 파일 `SCHEMAS.md`가 나은가?** → A: schema-rules.yaml 밖 = 검증 체계 밖. 섹션 추가가 비용 대비 효용 우위.

### 스키마

```yaml
# schema-rules.yaml에 추가
data_schemas:
  name: "Data Schemas"
  required: false
  allow_none: true
  description: "모듈의 공개 타입 정의 (다른 모듈이 참조하는 타입들)"
```

### 형식 (자유 마크다운, 권장 패턴)

```markdown
## Data Schemas

### Claims
| 필드 | 타입 | 설명 |
|------|------|------|
| userId | string | 사용자 식별자 |
| exp | number | 만료 시각 (Unix timestamp, UTC) |
| permissions | string[] | 권한 목록 |

### TokenPair
| 필드 | 타입 | 설명 |
|------|------|------|
| accessToken | string (JWT) | 단기 액세스 토큰 |
| refreshToken | string (JWT) | 장기 갱신 토큰 |

### AuthError
| 필드 | 타입 | 값 |
|------|------|-----|
| code | AUTH_ERROR_CODE | EXPIRED \| INVALID_SIGNATURE \| SESSION_LIMIT \| REFRESH_EXPIRED |
| message | string | 사람 읽기용 메시지 |
```

### Constraints와의 관계

Constraints는 행동 계약에 집중, Data Schemas는 타입 정의에 집중:

```markdown
## Constraints
- validateToken(token: string) → Claims | AuthError  ← 행동만
- refresh token TTL ≤ 720h

## Data Schemas
### Claims
...                                                  ← 구조만
```

### 파이프라인 영향

| 명령 | 변경 내용 |
|------|-----------|
| `/decompile` | format-analysis → Data Schemas 자동 생성 (ExportedType 데이터 활용) |
| `/compile` | Data Schemas → 조건부 런타임 타입 검증 테스트 (타입 시스템 없는 언어에서만) |
| `/validate --strict` | Data Schemas drift 검출: 문서 타입 ↔ 코드 ExportedType 비교 |
| `/impl` | 타입 설계 포함한 DEVELOPERS.md 생성 가이드 업데이트 |

## 변경 2: `### Configuration` (Operations 서브섹션, 선택)

### 동기

현재 Operations > 배포:
```markdown
### 배포
- SECRET_KEY 환경변수 필수
- JWT_PUBLIC_KEY 환경변수 로드
```

타입, 필수여부, 기본값이 없다. 새 개발자가 환경 설정을 파악하려면 소스코드를 봐야 한다.

### Socratic 검증

- **Q: Operations가 선택 섹션이라 Configuration도 건너뛸 수 있지 않나?** → A: 설정이 있는 모듈은 Operations 작성을 권장한다는 인식 강화가 목표. 필수화는 "None" 형식주의를 유발.
- **Q: code_analyzer가 env_vars를 추출하는가?** → A: 현재 미추출. 언어별 패턴은 단순해서 추가 비용 적음 (`process.env.X`, `os.environ["X"]`, `os.Getenv("X")`, `env::var("X")`).

### 스키마

```yaml
# schema-rules.yaml operations.subsections에 추가
- "Configuration|설정"
```

### 형식 (권장 패턴)

```markdown
### Configuration

| 환경변수 | 타입 | 필수/기본값 | 설명 |
|----------|------|-----------|------|
| JWT_PUBLIC_KEY | string | required | RS256 공개키 (PEM 형식) |
| TOKEN_TTL_HOURS | number | default: 168 | access token 유효 시간 (시간 단위) |
| MAX_SESSIONS | number | default: 5 | 사용자당 최대 동시 세션 수 |
```

### 파이프라인 영향

| 명령 | 변경 내용 |
|------|-----------|
| `/decompile` | code_analyzer에 env_vars 추출 추가 → Configuration 자동 생성 |
| `/compile` | Configuration → 설정 로딩 코드 + 누락 시 실패 처리 생성 |
| `/validate` | Configuration에 선언된 env_vars가 코드에서 실제 참조되는지 검증 |

## 변경 3: `## Flows` (DEVELOPERS.md, 선택, project_root only)

### 동기

개별 모듈의 Constraints로는 "사용자가 로그인하면 어떤 순서로 무슨 일이 벌어지는가"를 알 수 없다.
시스템 수준 실행 흐름은 project root에서만 기술 가능하다 (INV-1: 자식 → 부모 참조 불가).

### Socratic 검증

- **Q: CLAUDE.md에 Flows를 넣으면 안 되나?** → A: Flows는 기술적 실행 순서 = DEVELOPERS.md 영역. CLAUDE.md는 WHY(요구사항) 전용.
- **Q: 별도 `FLOWS.md`로 분리?** → A: 검증 체계 밖 = 유지 비용만 증가. DEVELOPERS.md 섹션 추가로 충분.
- **Q: project_root만 허용 조건 근거는?** → A: INV-1 트리 의존성 — 모듈 DEVELOPERS.md는 자식만 참조 가능. 크로스 모듈 흐름은 공통 조상(root)에서만 기술 가능.

### 스키마

```yaml
# schema-rules.yaml developers_sections에 추가
flows:
  name: "Flows"
  required: false
  condition: "is_project_root"
  condition_type: "dynamic"
  allow_none: true
  description: "시스템 수준 use case 실행 흐름 (project root only)"
```

### 형식 (권장 패턴)

```markdown
## Flows

### 사용자 로그인
1. `api/auth` ← POST /login { email, password }
2. `domain/auth` — validateCredentials(email, password) → Session | AuthError
3. `domain/session` — createSession(userId) → SessionToken
4. `api/auth` → Response 200 { token: SessionToken } | Response 401 { error: AuthError }

### JWT 검증 (매 요청)
1. `middleware/auth` — extractToken(headers.Authorization) → JWT | null
2. `domain/auth` — validateToken(JWT) → Claims | AuthError
3. `middleware/auth` — req.user = Claims 주입 | Response 401
```

**형식 규칙**:
- 각 단계: `` `모듈/경로` — 함수명(입력) → 출력 ``
- 모듈 경로는 project root 상대 경로
- 데이터 타입은 Data Schemas 또는 Constraints에서 정의된 타입 참조

### 파이프라인 영향

| 명령 | 변경 내용 |
|------|-----------|
| `/decompile` (root) | 모듈 간 호출 그래프에서 주요 Flows 역추출 시도 |
| `/validate` | Flow에 언급된 모듈 경로가 실제 존재하는지 CLI 결정론적 검증 |
| `/validate --strict` | Flow 단계의 함수 시그니처가 해당 모듈 Constraints와 일치하는지 검증 |

## 목표 달성 검증

변경 후 "소스코드 없이 공개 API 계약 수준에서 시스템 전체 동작 파악" 조건:

| 질문 | 변경 전 | 변경 후 |
|------|---------|---------|
| 이 모듈의 공개 함수 시그니처는? | Constraints (불완전, 타입 중복) | Constraints + Data Schemas (명확) |
| 반환 타입의 필드 구조는? | 인라인 산재 | Data Schemas 중앙화 |
| 시스템에서 로그인이 어떻게 처리되는가? | 알 수 없음 | Flows (project root) |
| 이 모듈에 필요한 환경변수는? | 배포 섹션 산재 | Configuration 테이블 |
| 내부 구현 로직은? | — | 의도적 제외 (scope 밖) |

## 미결 사항 (구현 시 결정)

1. **Data Schemas 형식**: 마크다운 테이블 vs code block (TypeScript interface 등). 언어 중립적 권장 형식 정의 필요.
2. **Flows 역추출 완전성**: `/decompile`에서 호출 그래프 역추출은 정적 분석으로 완전하지 않을 수 있음. "best-effort" 표기 필요.
3. **Configuration 자동 검증 범위**: 선언된 env_vars가 코드에 없으면 warning인가 error인가? (권장: `--strict` 모드에서 warning)
